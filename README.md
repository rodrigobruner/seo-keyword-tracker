# SEO Keyword Tracker

A small SEO keyword tracker for a marketing agency. A user signs in and sees their client's crawled pages, each with the keywords it likely ranks for, the SEO issues found on it, and its rank position over time — and can point the crawler at a new website to pull it in.

Take-home built with **Node + TypeScript** (Express, **raw SQL on PostgreSQL**) and **React** (Vite). This README is the map; the full design lives in [`docs/`](docs/).

## Stack

PostgreSQL · Node 24 (LTS) + TypeScript + Express + `node-postgres` (raw SQL, **no ORM**) · React + Vite + TS + CSS Modules + TanStack Query + Recharts · npm-workspaces monorepo (`api` + `web`; the crawl worker is a second entrypoint of `api`, draining a Postgres `SKIP LOCKED` queue).

## How to run

Requires **Node 24**. The quickest path is the guided setup — it asks whether to
use Docker or your own Postgres, generates `.env` (secrets included), migrates,
optionally seeds, and can start the app:

```bash
npm run setup
```

```bash
# 4. Run everything (API :4000 · worker · web :5173)
npm run dev
```

## Data: what's real vs simulated

Per the brief, *"positions are invented… the pages and keywords are not invented — they come from the live website."* So:

- **Real** — pages (crawled from the live site), the likely **keywords** (RAKE over the actual HTML), and the **SEO issues** (detected from the markup). Sitemap discovery runs against any site, nothing hardcoded.
- **Simulated** — the **rank positions over time** are generated by a seeded random walk, not real SERP data. The seed exercises the full data model, scale (≥50k snapshots) and charts without a paid SERP API; swapping in a real source (e.g. Search Console) only changes who fills `rank_snapshots.position`.

## Decisions, at a glance

Raw SQL (no ORM) to showcase schema + performance · single repo, two workspaces · worker + Postgres `SKIP LOCKED` queue for crawling · JWT-in-httpOnly-cookie auth · timezone fixed to America/Toronto (per the brief) · SEO thresholds aligned to Lighthouse/Yoast · console UI on a brand-aligned theme-token system. Every choice is sized to the challenge; the scale path for each is in [`docs/scaling.md`](docs/scaling.md). Full rationale in [`docs/decisions.md`](docs/decisions.md).

## Unfinished / what's next

- **Rank data is simulated** by design (the brief says positions are invented). In production the same `rank_snapshots` table would be filled from Google Search Console / a SERP API on a schedule — no schema change, just a new source.
- **Column sorting** — the pages endpoint already supports `sort`/`dir` (with a safe allowlist), but the UI doesn't expose it yet; wiring clickable headers is the obvious next step.
- **Frontend tests** — the backend has unit + DB-integration tests; the frontend has none by scope. A Vitest + Testing Library harness over the pages/add-client flows would be next.
- The production evolution for every area (auth revocation/MFA, partitioning `rank_snapshots`, per-user timezone, a CSP on the SPA, per-user crawl quotas, …) is laid out in [`docs/scaling.md`](docs/scaling.md) — deliberately not built for this scope.
