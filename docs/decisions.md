# Decisions

Why things are built the way they are. One short entry per decision, newest at the bottom.

**Guiding principle:** every choice here is right-sized for the take-home's scope. Where a decision would change under real load or a real product, the evolution path is documented in `scaling.md` — the simplicity (and the deliberate bits of structure) are scoped choices, not oversights.

---

**SQL over an ORM** — Hand-written SQL on `node-postgres`, no Prisma. The brief grades schema design and performance at 50k+ rows, so I keep the SQL in plain sight instead of behind an ORM. Safety nets: parameterized queries everywhere, hand-written row types, and `zod` at the API edges.

**Single repo, two workspaces** — The brief asks for one public repo as the whole submission, and it's one app (api + web) for one reviewer. npm workspaces give a single clone-and-run and atomic cross-cutting commits, with no monorepo tooling. Separate repos / microservices would be over-engineering at this size.

**Infra stays at root** — The infra surface is just `docker-compose.yml` (Postgres), `.github/workflows/` (pinned there by GitHub), and `.env.example`. An `infra/` dir would hold a single movable file and break the conventional "clone and run". Revisit if infra grows (app Dockerfiles, IaC, deploy scripts).

**Backend stack** — Node + TypeScript + Express for a small REST API (Nest too heavy, Fastify no real gain here). `pg` + raw SQL for data, `zod` for input, `bcrypt` + JWT-in-an-httpOnly-cookie for auth. The crawler uses native `fetch` + `cheerio` + `fast-xml-parser`; `pg-copy-streams` loads the 50k seed; `vitest` for tests and `tsx` to run TS directly. Bias throughout: fewest dependencies, every pick favors what's being graded.

**Node 24 LTS** — Node 20 hit end-of-life in April 2026, so we target the current well-established LTS: supported to April 2028, broad tooling support. (Node 26 is newer but had been LTS only weeks at the time.) Pinned via `.nvmrc`, `engines` in `package.json`, and the CI matrix.

**Frontend stack** — React + Vite + TS, React Router, and an auth Context that reads the httpOnly-cookie session via `/auth/me` (the token never touches the frontend). TanStack Query for server state — it earns its keep polling the crawl status until `READY` and caching the list/detail. CSS Modules (scoped, no extra tooling) over Tailwind. Page-detail history shows a Recharts line chart plus a table — visual trend and exact values. Timezone via native `Intl` (UTC→Toronto). Forms stay plain controlled inputs: only login and add-client (2–3 fields each), so `react-hook-form` wouldn't pay its cost.

**Authentication** — Email + password, hashed with bcrypt (cost 12). The session is a stateless JWT signed with `SESSION_SECRET`, carried in an `httpOnly` + `SameSite=Lax` + `Secure` (prod) cookie (~7d) — it survives a refresh, is never exposed to JS, and needs no session table. A `requireAuth` middleware verifies the cookie and scopes every query by `user_id` (cross-user access → 404). Login returns a generic error and runs a dummy hash on unknown emails to avoid user enumeration; `SameSite=Lax` + same-origin covers CSRF at this scope. No revocation needed here — logout just clears the cookie.

**Database schema** — Six tables; full spec + ER diagram in `docs/database.md`. Surrogate `bigint` keys (tenancy makes sequential ids safe → 404, and they keep the big index compact). `rank_snapshots` is keyed by the composite `(page_id, keyword_id, captured_at)` with no surrogate id — one btree is identity + one-per-day + the latest-position query. `captured_at` is `timestamptz` UTC (preserves the Toronto day-shift the brief probes). Keywords are global/deduped via an M:N link carrying `relevance`; SEO issues are denormalized findings (not a catalog); `position` is a strict `smallint` 1..100. Every choice fits the take-home's scope; the production evolution path for each is in `docs/scaling.md`.

**Timezone fixed to Toronto** — Snapshots are stored in UTC; display and date-range filtering convert to **America/Toronto**, not the viewer's browser timezone. The brief explicitly states *"The person using the app is in Toronto"*, so a fixed zone is the faithful reading (browser detection could show a non-Toronto reviewer the wrong zone). The zone is a single config value (env, default `America/Toronto`) rather than hardcoded throughout; display formats via `Intl` with that `timeZone`. Per-user timezone is the production path (see `scaling.md`).

**Async crawl: worker + Postgres queue** — Adding a client enqueues a `crawl_jobs` row and returns immediately (`client.crawl_status = PENDING`); a separate **worker** entrypoint consumes the queue with `SELECT … FOR UPDATE SKIP LOCKED`, so multiple worker instances run safely and **scale horizontally by adding containers** — with **no broker**, since the queue is the Postgres we already have. Chosen over an in-process queue (doesn't scale, dies with the process) and over Redis/BullMQ (extra infra the brief doesn't need). Scoped note: this is deliberately a touch more structure than 2×15 pages needs — picked to show a durable, horizontally-scalable pattern with **zero new infra**; the scale story lives in `scaling.md`, and a plain in-process queue is the ready fallback if time pressures the core screens. Benefits: jobs are **durable** (survive API/worker restarts) and **observable for free** (status/attempts/timing/`last_error` are all queryable; a reaper requeues jobs stuck past a visibility timeout, replacing boot-recovery). The worker runs in-process in dev (one `npm run dev`) and as its own container in prod. Crawl is best-effort per page — `READY` with whatever succeeded, `FAILED` only if discovery fails or zero pages — and creates no rank snapshots (seed only). Broker-grade features (priorities, delays, DLQ) would be the only reason to move to Redis/SQS later.

Packaging: the worker is a **second entrypoint in the `api` workspace** (`src/worker.ts`), **not a third workspace** — it reuses the API's db pool, repositories, crawl logic, and config. The monorepo stays two workspaces (`api`, `web`); prod builds one image and runs two commands from it (`dist/index.js` / `dist/worker.js`), each scalable independently.

**SEO heuristics (keywords & issues)** — Revised after market research (changed from our first naive plan). **Keywords:** RAKE-style candidate phrases + SEO zone-weighting (title 5, h1 4, meta 3, h2/h3 & slug 2, body 1), keep score ≥ 2, top 15, `relevance` normalized 0..1; optional corpus TF-IDF across the 15 pages (time-permitting — the only part that adds real complexity, as it couples pages into a two-phase pass). **Issues:** on-page checks with thresholds aligned to Lighthouse/Yoast — title 30/60, **meta 120/160** (was 50/160), single H1, img alt, thin < 300 words, canonical, viewport — plus `NOINDEX` (HIGH) and `NON_DESCRIPTIVE_LINKS` (LOW) from Lighthouse, and optional `KEYWORD_STUFFING` (>3%) from Yoast. All weights/thresholds live in config; a small RAKE is implemented in-house (no heavy dep). Rationale: industry-aligned numbers beat invented ones, and reusing proven strategy is cheaper and more credible than reinventing. Detail + sources in `docs/heuristics.md`.

**Design: console layout + theme tokens** — UI is the SEO-console structure (dark brand-navy sidebar + light canvas, a few stat cards, dense sortable table) with a minimal finish (neutral surfaces, hairline borders, one accent, strong type scale); responsive desktop-first. Page detail toggles **Chart ↔ Table** via a segmented control (default Chart) — two views of the same data. Everything is driven by a **theme-token layer** (CSS custom properties, two-tier primitive→semantic colors + spacing/type/radius/shadow scales): **no hardcoded colors or common sizes in component CSS**, so the identity can be retuned or swapped in one place. Palette is **locked to ProductiveShop's real theme tokens**: indigo `#6161ff` as the accent on light surfaces, lime `#d1f960` (dark text) on the dark sidebar (matching their `.site-header__nav`), navy `#112235` sidebar, the brand grey scale, and the Satoshi/Switzer fonts. Detail in `docs/design.md`.

**Crawl hardening (SSRF + resilience)** — The crawler fetches user-supplied URLs, so it defends against SSRF/abuse: only `http(s)`, reject when the resolved IP is loopback/private/link-local/reserved, re-check every redirect target, and cap timeout + response size + `content-type` (html/xml only). Separately, the seed is made resilient to its live dependencies (semrush/yoast): timeouts + retries + a realistic UA, plus committed **fallback fixtures** (cached sitemap/HTML) so `npm run seed` never hard-fails if a site is slow, changed, or blocks us — protecting the brief's "it must run from a clean clone".

**Tenancy proven by an integration test** — "User A can't reach User B by changing an id" is an explicit grading criterion, so it's verified end-to-end: a supertest HTTP test against a disposable Postgres asserts a 404 on cross-user access to a page/client — not just a unit test of the SQL.

**Security posture** — Controls sized to the challenge, enforced centrally. **AuthZ:** every resource scoped by `user_id` (cross-user → 404, integration-tested). **Injection:** parameterized SQL everywhere + an **allowlist for `ORDER BY`** (sort injection); crawled content always rendered as untrusted text (no `dangerouslySetInnerHTML`). **Auth:** bcrypt; JWT in an httpOnly/SameSite=Lax/Secure cookie with the verify **algorithm pinned** (`HS256`); `SESSION_SECRET` validated strong at boot (fail fast); login rate-limited + generic errors + dummy-hash. **Crawl/SSRF:** `http(s)` + ports 80/443 only, reject private/loopback/link-local/reserved resolved IPs **incl. DNS-rebinding** (connect to the validated IP), re-check redirects, and bound recursion depth / sitemap count / response size / parsed entries (DoS); **client creation is rate-limited per user** — each create triggers a crawl, so this caps crawl resource-abuse / outbound-fetch amplification (integration-tested). **Edges:** `helmet` headers + strict prod CORS (explicit origin, never `*`), body-size and `pageSize` caps, never return `password_hash`, generic error middleware (no stack/SQL leak), lockfile + `npm audit` in CI. CSRF is covered by SameSite=Lax + same-origin + JSON. Production-grade hardening lives in `scaling.md` (Security).

**Sitemap-discovery robustness** — Discovery stays generic but covers more of the real web, because the reviewer can point "Add client" at any site. There is no standard sitemap filename (sitemaps.org leaves location open), so seeds are tried by authority: robots.txt `Sitemap:` (the only spec'd mechanism) → the homepage's `<link rel="sitemap">` (site-declared, weak but better than guessing) → an expanded list of high-probability paths (`/sitemap.xml`, `/sitemap_index.xml`, `/wp-sitemap.xml` for WordPress core, `.gz` variants, `/sitemap.txt`). Content handling grew to match: the HTTP layer gunzips `.xml.gz` payloads (magic-byte detection, output capped to the size guard against zip bombs), and the parser accepts the protocol's plain-text format (one URL per line) in addition to XML urlset/index. The homepage is only fetched when robots is silent, so the happy path stays one request.

**Client management + delete (scope extension)** — The brief's screen 4 is "Add a client"; we broadened it to a **Clients** page (add form kept prominent) with a list of the user's clients and a **delete** action (inline confirm). Delete is a deliberate add beyond the brief, chosen because it's low-risk (schema already cascades client → pages → keywords/issues/snapshots + crawl_jobs) and because `DELETE /clients/:id` **exercises tenancy on a mutation** (cross-user → 404, integration-tested with a cascade assertion), reinforcing the graded isolation criterion rather than diluting it. The "Add a client" affordance the brief names stays first-class.
